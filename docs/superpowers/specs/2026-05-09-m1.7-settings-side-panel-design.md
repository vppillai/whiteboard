# M1.7 — Settings side panel + sync-ready schema

**Date:** 2026-05-09
**Status:** Spec — pending implementation plan
**Milestone:** M1.7 (see [docs/milestones.md](../../milestones.md))
**Related ADR:** [0010-settings-data-model](../../decisions/0010-settings-data-model.md) (to be written during implementation)

## 1. Goal

Ship a discoverable, pen-friendly settings side panel. The panel exposes brush-preset tuning, custom color swatches, grid configuration, theme selection, and a Reset-to-defaults footer. Behind the panel, redesign the settings storage shape into a versioned schema that's ready for future cross-device sync without committing to any sync protocol yet.

## 2. Locked decisions

Captured during brainstorming (2026-05-09):

| Decision | Lock |
|---|---|
| Panel sections | All 7: Brush presets · Custom swatches · Fonts (placeholder) · Grid · Theme · Advanced · Reset to defaults footer |
| Hotkey | `Cmd/Ctrl + ,` |
| Slide direction | From the right edge |
| Slide behavior | Overlay (canvas keeps full width; panel hovers above) |
| Custom-swatch UX | Integrated grid in color picker; custom swatches distinguished by 1.5 px ring; "+" tile last |
| Curated palette | Unchanged (Tailwind 500 saturated; pastels are user-added via "+") |
| Hex input | Sub-popover with `#______` text field + native OS color picker + Add button |
| Brush preset editability | `size`, `opacity`, `pressureGamma` per brush in Brush presets section. Remaining 8 BrushConfig fields go to Advanced (collapsed by default) |
| Reset scope | Scope B — preferences + custom swatches + recent colors. Camera, strokes, IDB untouched. Theme deliberately preserved (see § 9) |
| Schema migration | Strategy A — eager migrate-on-load |
| Custom swatch storage | `settings.customSwatches: string[]` |
| Recent colors | Folded into `settings.recentColors: string[]` |
| Panel persistence | Always starts closed on page load |
| Click-outside | No-op (panel is deliberate, not transient) |

## 3. Non-goals

Out of scope for M1.7; tracked in § 13:

- Adding new brush presets beyond the SPEC's 5. Built-in 5 are editable; CRUD on the preset list is M2+.
- Per-stroke text rendering (Fonts section ships as a placeholder; the actual Text tool is M2+).
- Backend sync. Schema reserves `syncedAt?` and `remoteId?`; no transport.
- Touch / iPad-specific panel tuning. Pen + keyboard cover Wacom Intuos workflow; iPad polish is post-v1 (SPEC § 10 Backlog).
- Pressure curve UI editor (SPEC § 4.4's draggable-midpoint graph). The slider in Brush presets covers the gamma scalar; the full graph editor is M2.

## 4. Architecture

Two new primitives + small refactor of the existing destructive-confirm flow.

### 4.1 New primitive: `apps/web/src/sidepanel.ts`

A side panel is structurally distinct from the existing popover system:

| Property | Popover (`popover.ts`) | Side panel (`sidepanel.ts`) |
|---|---|---|
| Anchor | Pointer position (transient) | Right edge (persistent location) |
| Lifetime | Single-instance, transient | Single-instance, deliberate |
| Dismissal | Click-outside, Esc, close button, opening another popover | Esc, close button, hotkey toggle, gear-pill toggle |
| Use case | Color picker, options menu, hex-input | Settings tree; future AI-features panel; future file-browser |

The panel primitive is **decoupled from M1.7 content**. Its API:

```ts
interface SidePanelOptions {
  title: string
  content: HTMLElement     // panel takes ownership
  onDismiss?: () => void
  refocusOnClose?: HTMLElement
}
function showSidePanel(opts: SidePanelOptions): SidePanel
function dismissSidePanel(): boolean
function isSidePanelOpen(): boolean
```

Behavior:

- Slides in from right with 200 ms ease-out. Width 320 px CSS.
- Overlay (canvas keeps its full width); panel sits over the canvas with a subtle backdrop.
- Esc dismisses. Click-outside is a no-op.
- Panel content scrolls vertically if it overflows.
- Re-opening the same panel is a toggle (close).

Why decoupled: ADR 0007 (tool surface) is precedent — M1.4's `Tool` interface was thin; two tools later, gaps showed (cursor + menu were splattered across `main.ts` and `toolmenu.ts`). Baking the primitive-vs-content split in from the start avoids that retrofit pass when M2's panels arrive.

### 4.2 New primitive: `apps/web/src/destructiveconfirm.ts`

Generalize the priming-toast pattern from `clearflow.ts`. The Reset-to-defaults flow is the second concrete user — the right time to extract.

```ts
interface DestructiveConfirmOptions {
  message: string
  confirmLabel: string
  onConfirm: () => void
  refocusOnClose?: HTMLElement
  windowMs?: number   // default 4000 ms
}
function createDestructiveConfirm(opts): {
  request(): void   // first call shows toast; second within window confirms
  cancel(): boolean // returns true if a pending toast was cancelled
}
```

`apps/web/src/clearflow.ts` collapses to a thin wrapper passing clear-board copy.

## 5. Schema design

### 5.1 v1 shape

```ts
// in apps/web/src/settings.ts
import type { BrushConfig } from '@whiteboard/shared'
import type { BrushId } from './brushes'

export type GridType = 'dots' | 'lines' | 'ruled' | 'none'
export type EraserSize = 'small' | 'medium' | 'large'

export interface SettingsV1 {
  schemaVersion: 1

  // existing scalars (preserved from v0)
  color: string
  brush: BrushId
  eraserSize: EraserSize
  grid: { type: GridType; spacing: number }

  // new in v1
  presets: Partial<Record<BrushId, Partial<Omit<BrushConfig, 'color'>>>>
  customSwatches: string[]   // hex strings, e.g. '#fbcfe8'
  recentColors: string[]      // most-recent first; capped at 6
  fonts: string[]             // reserved for Text tool (M2+)

  // reserved for future sync (post-v1)
  syncedAt?: number
  remoteId?: string
}
```

`eraserMode` remains intentionally **session-only** — not in `SettingsV1`. (Per existing rationale in `settings.ts`: Item is a niche surgical mode; persisting traps users in it across reloads.)

### 5.2 Sparse preset overrides

`presets[brushId]` carries only fields the user changed. The renderer composes effective config:

```ts
export function getEffectiveBrushConfig(brushId: BrushId, color: string): BrushConfig {
  const def = BRUSH_PRESETS[brushId]
  const override = state.presets[brushId] ?? {}
  return { ...def, ...override, color }
}
```

Empty `presets` (default state) yields exactly today's behavior — SPEC defaults always recoverable. "Reset this preset" in the panel = `delete state.presets[brushId]`.

### 5.3 Reserved sync fields

`syncedAt?: number` and `remoteId?: string` are explicit in `SettingsV1` from day one. No code touches them in v1. Their reservation:

- prevents future schema bump just to add them.
- documents intent visibly in the type.
- keeps the post-v1 sync layer from needing a v1 → v2 migration purely for two new optional fields.

Decisions deferred to the future sync milestone: conflict resolution, transport, auth. M1.7 commits to nothing about how sync works, only that the schema is ready.

### 5.4 Migration strategy: A — eager migrate-on-load

```ts
function load(): SettingsV1 {
  const raw = localStorage.getItem('whiteboard:settings')
  if (!raw) return clone(DEFAULTS)
  let parsed: unknown
  try {
    parsed = JSON.parse(raw)
  } catch {
    return clone(DEFAULTS)   // corrupted; reset
  }
  if (isV1(parsed)) return validate(parsed)
  // v0 (no schemaVersion): migrate
  const v1 = migrateFromV0(parsed)
  persist(v1)   // write back so subsequent loads see v1
  return v1
}
```

Properties:

- **Mechanical**: `migrateFromV0` only fills new fields with defaults; it never strips or transforms v0 data.
- **Idempotent**: `validate(v1)` produces identical output for already-v1 input.
- **Safe**: a buggy `migrate()` would surface as "all my settings are defaults" — bad UX but not data-loss-with-side-effects (v0 is overwritten the moment we write back). Mitigated by tests covering v0 → v1, malformed, partial-v1, and idempotent paths (§ 12.1).

### 5.5 `recentColors` is new in M1.7

The CHANGELOG M1.5 entry mentions an inline recent-colors row that "persists across reloads (max 6)." A code audit (`grep -rn "recent" apps/web/src/`) finds **no implementation** — the feature was scoped in CHANGELOG but never landed. Only three localStorage keys exist today: `whiteboard:theme`, `whiteboard:settings`, `whiteboard:view`.

M1.7 implements recent-colors for the first time, directly into `settings.recentColors` (no parallel storage to migrate from). Picker's `setColor` flow calls `pushRecentColor(hex)` which prepends, dedupes, and caps at 6. The CHANGELOG should be corrected at M1.7 close to clarify that the recent-colors row was deferred from M1.5 to M1.7.

Rationale for putting it directly in settings (rather than its own key): Reset-to-defaults Scope B wipes recent colors via the same `resetAll()` path as everything else. Sync-readiness is also better when a single key carries the whole user state.

## 6. Side panel UI structure

The panel content lives in `apps/web/src/settings/panel-content.ts` and mounts into the `sidepanel.ts` primitive's content slot.

### 6.1 Sections (top to bottom)

#### 6.1.1 Brush presets

Five cards stacked vertically, one per brush in the BRUSH_IDS order (pen, marker, pencil, highlighter, brush). Each card:

```
┌────────────────────────────────────────────┐
│ [icon]  Pen                                │
│                                            │
│   Size            ─────●─────  3.5         │
│   Opacity         ───────●───  0.94        │
│   Pressure γ      ────●──────  1.3         │
│                                            │
│   Reset this preset                        │
└────────────────────────────────────────────┘
```

- Sliders are native `<input type="range">` styled to match the existing pill aesthetic.
- Live update: changing a slider calls `setPresetField(brushId, field, value)` → `state.presets[brushId]` sparse-updates → persists → emits change → renderer re-reads on next stroke. Existing committed strokes are unchanged (their `brush` is captured at pointerdown).
- "Reset this preset" link calls `clearPreset(brushId)` (deletes the entry from `presets`); next stroke uses SPEC default.
- Cards do not collapse in v1 (5 × 3 sliders fits comfortably; the Advanced section's per-brush card *does* collapse).

Slider ranges:

- Size: 1–24 px, step 0.5.
- Opacity: 0–1, step 0.02.
- Pressure γ: 0.5–3.0, step 0.1.

#### 6.1.2 Custom swatches

```
─── Custom swatches ───────────────
  ●   #fbcfe8         [×]
  ●   #7dd3fc         [×]
  ●   #6ee7b7         [×]
   + Add custom color
```

Each row: 16 px swatch preview · uppercase hex value · delete (×) button. Order is creation order; manual reorder defers to M2.

"+ Add custom color" opens the same `swatchadd.ts` UI used by the color picker's "+" tile (§ 7).

Empty state: italic subtitle *"Add a custom color to use across the board."*

#### 6.1.3 Fonts (placeholder)

```
─── Fonts ──────────────────────────
   Reserved for the Text tool (M2+).
```

No interactive controls. Section visible so users see the future surface; schema reserves the field. (Removing the section visually contradicts the locked all-7-sections scope.)

#### 6.1.4 Grid

Duplicate of the existing options popover content:

```
─── Grid ───────────────────────────
   Type      [Dots] [Lines] [Ruled] [None]
   Spacing   [16] [24] [32] [48]
```

Reads/writes the same `settings.grid`; both UI surfaces (popover and panel) update synchronously via the existing `onChange()` subscription.

#### 6.1.5 Theme

```
─── Theme ──────────────────────────
   [Light] [Dark] [System]
```

Three-way toggle. Reads/writes the existing theme module. The `T` key continues to cycle.

#### 6.1.6 Advanced

```
─── Advanced ───────────────────────
   ▶ Show advanced
```

Collapsed by default. Expanded:

Per-brush card with the remaining 8 BrushConfig knobs (`thinning`, `smoothing`, `streamline`, `taperStart`, `taperEnd`, `capStart`, `capEnd`). Same sparse-override semantics as Brush presets. "Reset this preset" link covers both Brush-preset and Advanced overrides for the same brush.

Why collapsed: 5 brushes × 8 knobs = 40 controls. Power-user surface; not on the casual path.

#### 6.1.7 Reset to defaults (footer)

```
═══════════════════════════════════════
        [ Reset to defaults ]
```

Red destructive button. Click → `resetflow.request()`:

> *"Reset all settings? Custom swatches and recent colors will be cleared."*
>
> [Cancel] [Reset]

Confirm → `settings.resetAll()`:

- `state.presets` → `{}`
- `state.customSwatches` → `[]`
- `state.recentColors` → `[]`
- `state.color` → `DEFAULTS.color` (`'ink'`)
- `state.brush` → `DEFAULTS.brush` (`'pen'`)
- `state.eraserSize` → `DEFAULTS.eraserSize` (`'medium'`)
- `state.grid` → `{ ...DEFAULTS.grid }`
- `state.eraserMode` (session) → `'wipe'`
- **theme is intentionally NOT reset** (see § 9)

Persist, emit, refocus canvas.

### 6.2 Toggle / dismiss behavior

| Path | Action |
|---|---|
| `Cmd/Ctrl + ,` | Toggle (open if closed, close if open) |
| Right-click TOOL menu → SETTINGS row | Open / toggle |
| Bottom-right pill, gear zone | Open / toggle |
| Esc (when panel is focused) | Close |
| X close button in panel header | Close |
| Click outside panel | **No-op** (deliberate UI; matches clear-flow toast) |
| Page reload | Always starts closed |

Open animation: 200 ms ease-out slide-in from right. Close: 150 ms ease-in slide-out.

### 6.3 Pen-friendly considerations

- Hit targets ≥ 32 px (per existing pill / popover conventions).
- Slider thumb is 20 px diameter (large enough to grab with pen tip on Intuos).
- The OS color picker (`<input type="color">`) is the easiest "pick a color" UX with a pen — single tap launches the OS picker, OS handles the color-wheel interaction.
- Closing the panel hands focus back to `#app` (per existing pattern in `clearflow.ts`) so subsequent keystrokes reach the canvas.

### 6.4 Why overlay, not push

A push layout means opening the panel changes where every screen-pixel maps to a board-coord — a stroke the user is *looking at* visually shifts when the panel opens. On an indirect-input device (Intuos), where the pen is on the tablet but the eyes are on the screen, this kind of viewport jump is genuinely disorienting. Overlay keeps the canvas pinned and lets the panel hover above. Cost: a small sliver of canvas under the panel, which is fine because the user isn't drawing while interacting with settings.

## 7. Color picker integration

### 7.1 Integrated grid

`apps/web/src/colorpicker.ts` extended:

```
┌──────────────────────────┐
│  COLOR    [pin] [×]       │
│                            │
│  ●  ●  ●  ●  ●            │   ← curated row 1
│  ●  ●  ●  ●  ●            │   ← curated row 2
│  ◌* ◌* ◌* ◌* ◌* +         │   ← custom (with ring) + "+" tile
│                            │
│  RECENT                    │
│  ●  ●  ●  ●               │   ← recent-colors row
└──────────────────────────┘
```

Rendering order: 10 curated → N custom (each with the 1.5 px ring) → "+" tile (always last). Recent row below.

Custom row wraps after the curated row; "+" is always the trailing position regardless of custom count. Empty custom palette → grid shows curated + "+".

### 7.2 The "+" tile sub-popover (`swatchadd.ts`)

```
    ┌─────────────────────────┐
    │  Add custom color        │
    │                          │
    │  [#______]   [🎨]        │
    │  ┌──┐                    │
    │  │  │ preview            │
    │  └──┘                    │
    │                          │
    │   [Cancel]  [Add]        │
    └─────────────────────────┘
```

- Hex text input: validates `^#?[0-9a-fA-F]{6}$`. Auto-prepends `#` on save. Updates preview live.
- 🎨 button: hidden `<input type="color">`. Click → OS color picker. On change → fills hex field.
- Preview: 24 px swatch showing the parsed value or empty if invalid.
- "Add" button: enabled only on valid hex AND the hex is not already in `settings.customSwatches` (curated palette and recent-colors are not checked — duplicates with curated are allowed because the user might want a custom version of an existing color, e.g. a slightly different red). Click → `addCustomSwatch(hex)` → settings persists → sub-popover dismisses → picker re-renders with new tile.
- Esc: dismiss sub-popover. Esc again: dismiss parent picker.

### 7.3 Reuse in panel "+ Add custom color"

The Custom swatches section's add button opens the same `addSwatchUI()` component (rendered inline into the panel content area, not as a sub-popover — there's nothing for it to anchor to). One component, two render contexts.

### 7.4 Edge cases

- Duplicate hex in `customSwatches` → no-op silently (set semantics).
- Invalid hex → "Add" disabled.
- Custom swatches unbounded in storage; UI caps at ~24 visible inline; overflow → "Manage in Settings…" link to the panel.

## 8. Reset-to-defaults flow

See § 6.1.7 for the UI; full mechanics:

```ts
// apps/web/src/resetflow.ts
import { createDestructiveConfirm } from './destructiveconfirm'
import { resetAll } from './settings'

export function createResetFlow(opts: { appEl: HTMLElement }) {
  return createDestructiveConfirm({
    message: 'Reset all settings? Custom swatches and recent colors will be cleared.',
    confirmLabel: 'Reset',
    onConfirm: resetAll,
    refocusOnClose: opts.appEl,
    windowMs: 4000,
  })
}
```

The Reset button in the panel footer wires its click to `resetflow.request()`.

The toast appears anchored to the bottom of the viewport (existing `#whiteboard-toast` element in `clearflow.ts` becomes a shared host inside `destructiveconfirm.ts`). Only one destructive toast can be open at a time — opening a second cancels the first (matches the popover single-instance behavior).

## 9. Theme exception

Reset-to-defaults Scope B (locked) wipes "preferences." Theme is technically a preference, but it is *not* reset by `resetAll()`.

Structural reason: theme lives in its own localStorage key (`whiteboard:theme`, owned by `theme.ts`), not in `whiteboard:settings`. `resetAll()` in `settings.ts` only mutates the in-memory state of the settings module and persists `whiteboard:settings`. It does not — and cannot, without crossing module boundaries — touch the theme module's storage. Keeping it that way is the right call:

- Theme reset would produce a jarring light/dark flash with no use-case payoff.
- "I clicked Reset and now my theme is wrong" is noise, not signal.
- Theme has its own dedicated path (`T` key + Theme section in panel) for reverting if the user actually wants system theme.
- The reset toast wording ("Custom swatches and recent colors will be cleared") doesn't mention theme — staying truthful matters for a destructive action.

If user feedback says strict Scope B is preferred (theme reset included), the change is: extend `resetAll()` to import and call `resetTheme()` from `theme.ts`, and update toast wording. Single-line module dependency, easy to add later.

## 10. Hotkey, pill, and right-click menu paths

### 10.1 Hotkey: `Cmd/Ctrl + ,`

In `keymap.ts`, add to the `Cmd/Ctrl-modified` block:

```ts
if (!shift && k === ',') {
  preventAndCall(e, handlers.togglePanel)
  return
}
```

`e.key` for comma is `,` on most layouts; the existing `k = e.key.toLowerCase()` handles it. The `!shift` filter rules out `<` from triggering the toggle.

### 10.2 Right-click menu: SETTINGS row

`toolmenu.ts` gets a new global section, sibling to the existing tool-owned sections:

```
─── (per-tool sections, e.g. COLOR / BRUSH or ERASER) ───
─── TOOL ───  (existing)
─── VIEW ───  (existing)
─── SETTINGS ─── (NEW)
   [   Settings…   ]   ← single full-width pill
─── (clear) ───  (existing)
```

The SETTINGS row is global chrome — not per-tool — so it lives in `toolmenu.ts` directly, not in `tool.renderContextualMenu()`.

### 10.3 Bottom-right pill: gear zone

`toolpill.ts` extends to two-zone:

```
   [⚙]  draw   ← gear zone | tool name + cycle zone
```

Tap zones:

- Gear icon (left) → `togglePanel()`.
- Tool name (right) → cycles tool (existing behavior).

Visual separation: thin divider between zones. Gear is a small SVG (12 px) at the left of the pill content. The pill remains one DOM element with two interactive children.

Decision rationale: separate pills cost screen space; one pill with two zones reads as "one settings-aware widget." Matches the existing pattern of overloading a single surface with multiple actions when conceptually adjacent.

## 12. Testing approach

### 12.1 Unit tests

The codebase has no test runner today. M1.7 sets up the first surface using bun's built-in `bun test` (already a dependency; no new tooling).

Tests target the highest-risk and most-pure surfaces:

**`migrate(input: unknown): SettingsV1`** — data-loss-risk surface.

| Input | Expected output |
|---|---|
| v0 shape (no `schemaVersion`): `{ color: '#ef4444', brush: 'pen', eraserSize: 'medium', grid: { type: 'dots', spacing: 24 } }` | v1 with all v0 fields preserved + new fields filled with defaults (`presets: {}`, `customSwatches: []`, `recentColors: []`, `fonts: []`) |
| Malformed JSON / nullish | `clone(DEFAULTS)` |
| Empty string | `clone(DEFAULTS)` |
| Partial v1 (missing `customSwatches`) | Same shape with `customSwatches: []` filled |
| Type-mismatched field (`eraserSize: 42`) | Field-level fallback to default; rest preserved |
| Already-v1 (well-formed) | Identical to input (idempotent) |

**`getEffectiveBrushConfig(brushId, color)`** — composition correctness.

| Override state | Expected |
|---|---|
| `presets[brushId]` undefined / empty | Identical to `BRUSH_PRESETS[brushId]` (with color spread) |
| `presets[brushId] = { size: 5 }` | SPEC default with size overridden to 5; all other fields unchanged |
| Color override | Honored over both default and override |

**`addCustomSwatch / removeCustomSwatch`** — set semantics.

| Sequence | Expected |
|---|---|
| add `#fbcfe8`, add `#fbcfe8` | Single entry (no duplicates) |
| add `#fbcfe8`, remove `#fbcfe8` | Empty array |
| remove `#nonexistent` | No-op (no error) |

### 12.2 Manual feel-test on Wacom Intuos

Per `docs/process.md` rule (tool / pointer / render changes need a feel-test scenario):

- Open panel via all four paths (`Cmd/Ctrl+,`, right-click → SETTINGS, gear zone, manual close + reopen).
- Edit each brush's size, opacity, pressureGamma sliders. Strokes after the edit reflect changes.
- "Reset this preset" link restores SPEC default for that brush only; other brushes' overrides survive.
- Add custom swatch via picker "+". Appears in picker + Custom swatches section.
- Add via panel "+ Add custom color". Appears in picker.
- Delete custom swatch in panel. Disappears from picker.
- Reset to defaults: priming-toast appears. Esc cancels. Press button or `Cmd/Ctrl+,` shortcut → wipes Scope-B targets. Theme survives.
- Reload page after edits → settings persist; panel starts closed.
- Manually mutate localStorage to v0 shape → reload → migration produces clean v1; legacy values preserved.
- Drawing during panel-open works (overlay; canvas is unobstructed under the panel).

### 12.3 Perf gates (regression check)

`?perftest=erase&n=500` and `?perftest=scale&n=500` should remain within the 16 ms frame budget after M1.7. The settings panel doesn't touch the render loop, but `getEffectiveBrushConfig()` runs on stroke start; verify it doesn't add measurable overhead.

## 13. Out-of-scope follow-ups

Not built in M1.7; tracked for later:

- **Adding new brush presets.** UI to create a 6th preset. Schema already supports it (`presets` is `Partial<Record<BrushId, ...>>`); adding a new `BrushId` requires a brushes.ts change, but the schema accepts the new key without migration.
- **Reorder custom swatches.** No drag-handle in the panel's Custom swatches list. Add when asked.
- **Pressure curve graph editor.** SPEC § 4.4 mentions a draggable midpoint + γ slider. M1.7 ships only the γ slider.
- **Backend sync.** Schema reserves `syncedAt?` and `remoteId?`. Implementation is post-v1.
- **Panel state persistence.** Currently always starts closed. If usage shows users want last-open state, add `panel.lastOpenAt` to the schema later.
- **Theme reset toggle.** If user feedback says "Reset should reset theme," that's a single-line change to `resetAll()` and a toast wording update (§ 9).
- **Per-brush color override.** Each brush could store its own color (rather than sharing the active color setting). Not requested; would require a UI decision about which color "wins" when switching brushes.
