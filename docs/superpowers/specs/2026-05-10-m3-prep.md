## 1. M3 Scope Summary

M3 ships the collaboration layer: a Bun HTTP + WebSocket server implementing a custom Y.js relay, room creation via `/b/<uuid-base32>` URLs, single-token owner auth, SQLite snapshot persistence via `bun:sqlite`, client-side `y-indexeddb` offline cache, ephemeral peer presence (cursors, anonymous names, colors), in-flight stroke crash recovery, and the migration path that converts the existing flat-IDB local board into a Y.Doc. The 30-second-idle and on-last-disconnect snapshot cadence, the 16-peer capacity target, and the single global `OWNER_TOKEN` env var are all already specified (SPEC § 5, § 6, § 8). This milestone produces a working multi-user board: two browsers pointing at the same `/b/<id>` URL see each other's strokes and cursors.

**Ships in M3:**

- Custom Y.js relay server (Bun.serve WebSocket + y-protocols)
- Room URL scheme `/b/<uuid-base32>`; UUIDv7 room IDs
- REST endpoints `POST /api/rooms` and `DELETE /api/rooms/:id`
- SQLite schema (`rooms` + `snapshots` tables) via `bun:sqlite`
- Snapshot write: every 30 s idle + on last-disconnect
- `y-indexeddb` client-side offline cache replacing the flat `storage.ts` IDB for synced rooms
- Ephemeral peer presence (cursor position, anonymous name, color)
- Migration from flat-IDB local board to Y.Doc on first room open
- In-flight stroke crash recovery (~2 s auto-save during long strokes)
- `OWNER_TOKEN` validation for admin REST operations
- Reconnect UX: informational toast on disconnect / reconnect

**Explicitly deferred (not M3):**

- Dockerfile / compose / deploy.sh — already shipped pre-M0; M4 is validation only (milestones.md M4)
- Multi-board list UI — SPEC § 10 Backlog
- Image paste / binary sync — SPEC § 10 Backlog (M5.1)
- User accounts / SSO / RBAC — SPEC § 1 Non-goals (permanent)
- AI features — M5–M7
- PWA install + service worker — M4.5
- Room idle TTL / auto-delete — M4 or later
- Room rename UI — M4 or post-v1 (the REST endpoint can ship at M3; the UI is not a gate)

## 3. Open Decisions That Need Brainstorming

### Decision 1 — Server relay: y-websocket npm server utilities vs. y-protocols from scratch

**Question.** The `y-websocket` npm package ships both a browser-side `WebsocketProvider` (used in browsers) and server-side utilities built on Node's `ws` library. Do we use those server utilities — with a Bun compatibility shim — or implement the relay from scratch using `y-protocols` (the lower-level primitive that `y-websocket` itself is built on)?

**Why it matters.** This shapes the entire server module. The `y-websocket` server utility handles the Y.js sync handshake (step1/step2 messages) and awareness broadcast — the non-trivial parts. But it is coupled to Node's `ws` EventEmitter API, which is structurally different from Bun's `ServerWebSocket` callback model (`Bun.serve`). Implementing from `y-protocols` is ~400–500 LOC of well-specified protocol handling (the ADR's own estimate: "small relay (~500 LOC)").

**Options.**

- **Option A — Use `y-websocket` server utility + Bun compatibility shim.** Wrap Bun's `ServerWebSocket` to look like a Node `ws` instance. Reduced initial coding; maintenance liability: every Bun update or `y-websocket` update can break the shim silently.

- **Option B — Implement relay from scratch using `y-protocols`.** Pure JS; no runtime dependencies. Exports `syncProtocol` (handshake) and `awarenessProtocol` (presence). Full control of room lifecycle, snapshot triggers, peer eviction, MAX_ROOMS enforcement. ADR 0003 explicitly anticipated this shape.

- **Option C — Vendor a copy of y-websocket server code, patched for Bun.** Copy ~200 LOC from `y-websocket/src/utils.js`; adapt to Bun; own the divergence. Avoids shim maintenance liability but trades it for fork maintenance liability.

**My lean: Option B.** ADR 0003 is explicit: "our own server implementation rather than the upstream demo server." `y-protocols` is the stable primitive. The ~400 LOC cost buys full control of room lifecycle, snapshot triggers, peer eviction, and MAX_ROOMS enforcement — none of which the generic y-websocket utility handles. Option A's compatibility shim is an invisible time bomb. Option C is a fork we'll regret at the next `y-websocket` update.

### Decision 2 — Auth model: what the owner token actually gates and how

**Question.** SPEC § 5 says `?token=<OWNER_TOKEN>` "unlocks: rename, delete, export-all." Architecture.md § 3.2 says the token "gates admin operations server-side." But the Y.js binary protocol has no "admin" concept — the relay either forwards a message or it doesn't. What exactly happens when the token is present on the WebSocket upgrade URL, and how do admin mutations (rename, delete) actually flow?

**Why it matters.** This is a handwaving zone in the current spec. Architecture.md § 3.1 already shows `DELETE /api/rooms/:id` as a REST endpoint — that's fine. But "rename" has no REST entry, and "export-all" is unspecified. If admin operations go over the WebSocket as custom messages, the relay must inspect binary frames, which ADR 0003 says not to do. The auth model needs to be completely specified before implementation begins.

**Options.**

- **Option A — Token gates REST only; WebSocket upgrade is token-optional with no behavioral change.** `DELETE /api/rooms/:id` and `PATCH /api/rooms/:id` (rename, to be added to the REST table) require `?token=<OWNER_TOKEN>` in the query string. The WS upgrade accepts and logs the token but changes nothing about relay behavior. Clean separation: REST for mutations, WS for sync.

- **Option B — Token on WS upgrade grants elevated relay privilege; admin intent messages arrive as custom envelopes outside Y.js binary.** Server marks the peer as "owner" for the session; custom messages trigger room operations. Requires custom framing — contradicts ADR 0003 ("binary protocol relayed unchanged").

- **Option C — Token gates REST; WS-session-validated admin presence is announced to peers as an awareness field.** WS upgrade validates token; server sets `isOwner: true` in the peer's awareness state; other peers render a visual indicator. Admin mutations still go via REST. Harmless cosmetic addition.

**My lean: Option A.** Admin operations are infrequent (rename, delete) and REST-native. Option B directly contradicts ADR 0003 — the relay relays the binary protocol unchanged; it does not inspect it. Option C (awareness `isOwner` field) is a nice-to-have UI detail, not a correctness requirement. Keep the WS channel for CRDT sync and awareness only. Add `PATCH /api/rooms/:id` to the REST table in architecture.md.

### Decision 3 — Room creation flow: explicit API call vs. lazy auto-create

**Question.** How does a room come into existence? `POST /api/rooms` is in the REST table (architecture.md § 3.1) but nothing specifies who calls it, when, or what the UX trigger is. The current app boots at `/` and starts drawing locally. At M3, boards live at `/b/<id>` and need a server-side room record.

**Why it matters.** This is the primary user-facing flow change at M3. The choice shapes what the home page (`/`) looks like, whether there's a "Share" modal, and whether local-only boards can ever exist without a server record.

**Options.**

- **Option A — Client generates UUIDv7 on "New board" click; navigates to `/b/<id>`; server auto-creates the room record on first WS connect.** The client never calls `POST /api/rooms` directly. "Share" is just copying the current URL. `POST /api/rooms` exists for programmatic/API use. No round-trip before drawing starts.

- **Option B — Explicit "Share" or "Create room" button calls `POST /api/rooms`, gets back the ID, navigates.** Local boards at `/` stay local until the user explicitly shares. Requires a server round-trip before the user sees their room URL — adds latency before collaboration starts.

- **Option C — Always in a room; `/` auto-creates and redirects to `/b/<id>`.** Every board is a room. Simplest sync model (always synced). Removes offline-drawing-without-server capability and creates a hard server dependency at every page load.

**My lean: Option A.** The "link-based sharing" language in SPEC § 0 Goals implies the URL IS the room. A "New board" button on `/` generates a client-side UUIDv7 and navigates to `/b/<id>`; the server creates the room record on the first WS connect. "Share" is the URL bar. No round-trip; no modal; drawing starts immediately. `POST /api/rooms` is for programmatic use by scripts/admins. Option C breaks the SPEC § 6 offline drawing guarantee and the M0-validated local use case. Option B adds latency to the most common flow.

### Decision 4 — Admin mutations: where does "rename room" live in the protocol?

**Question.** Architecture.md § 2.2 lists "rename" as a server admin responsibility. But `PATCH /api/rooms/:id` is not in the architecture.md REST table (only `POST` and `DELETE` appear). Room name is in SQLite (`rooms.name`). If rename is REST, how do connected peers learn the new name?

**Why it matters.** Room name is metadata, not board content. Putting rename in the Y.Doc conflates metadata with CRDT content. REST is the right shape, but a broadcast notification to peers is needed when the name changes. The notification channel (presence vs. a custom server-push message) needs to be defined.

**Options.**

- **Option A — Rename is `PATCH /api/rooms/:id` (REST, owner-token); server pushes a rename notification on the presence/awareness channel.** Peers receive the notification and update their room-name display. Clean mutation path; one-hop broadcast.

- **Option B — Rename deferred; not in M3 scope.** `rooms.name` is set at creation; no rename UI at M3. `DELETE` is the only admin mutation. Add rename at M4 or post-v1.

- **Option C — Rename via Y.Doc `roomMeta.name` Y.Map field.** The owner updates a top-level metadata field; peers see it via Y.js sync. Requires the server to validate that only the owner writes `roomMeta` — which means inspecting Y.js binary updates, contradicting ADR 0003.

**My lean: Option B for M3 scope; Option A as the specified design for when it ships.** Rename is non-critical for M3's primary exit criterion. Don't let it block the milestone. When it ships: REST PATCH + presence announcement. Option C is ruled out categorically by ADR 0003.

### Decision 5 — Y.Doc initialization order on server: snapshot load timing

**Question.** When a peer connects to a cold room (no in-memory Y.Doc), the server must load the SQLite snapshot before handling the Y.js sync handshake. With concurrent first-connects (two peers hitting the same cold room simultaneously), there is a potential race where both trigger a snapshot load and create separate Y.Docs, with the second one clobbering the first.

**Why it matters.** Getting this wrong means one peer's initial sync returns empty state, losing all previous work. This is a silent correctness failure.

**Options.**

- **Option A — Synchronous SQLite load on first connect; the room struct is set in the server's `Map<roomId, YDoc>` before the handshake is processed.** `bun:sqlite` is synchronous by default. JavaScript's single-threaded event loop means two WS upgrade handlers cannot truly execute in parallel — the second runs after the first has set the room in the map. No race in Bun's single-process model. Simple; add a comment explaining the single-thread assumption.

- **Option B — Per-room `Promise<YDoc>` in the room map; all connects for the same room await that promise.** Handles the concurrent-connect race explicitly regardless of runtime threading model. The upgrade: `roomMap.set(roomId, loadPromise)` first; subsequent connects `await roomMap.get(roomId)`.

- **Option C — Pre-load on HTTP GET for `/b/<id>` before WS connect.** HTTP GET warms the room; WS connect finds it warm. Adds HTTP–WS coordination complexity.

**My lean: Option A with a clear comment; note Option B as the upgrade path.** Bun is single-threaded: two "concurrent" WS upgrade handlers interleave in the event loop; they do not run in parallel. A `Map.has(roomId)` check plus synchronous SQLite read in the first handler completes before the second handler can run. This is correct for Bun's current execution model. Document the assumption explicitly so any future multi-threaded evolution triggers a review.

### Decision 6 — erasedStamps CRDT representation: nested Y.Array vs. plain JS array inside Y.Map

**Question.** `Stroke.erasedStamps` is currently typed as `{ x, y, r }[]` — a plain JS array. In a Y.Doc, Y.Map values use last-write-wins (LWW) semantics for concurrent key updates. If two peers simultaneously erase pixels on the same stroke, they each build a different `erasedStamps` array; Y.js picks one and discards the other, silently losing half the erasure.

**Why it matters.** This is a latent data-correctness bug. It is invisible in single-user testing and in sequential multi-user use. It surfaces under concurrent erasure of the same stroke — uncommon but not impossible at 16 peers. The fix is in the schema design and costs nothing at runtime. The decision gates the `packages/shared` typed Y.Doc wrappers and must be settled before any client sync code is written.

**Options.**

- **Option A — Store erasedStamps as a nested `Y.Array<Y.Map>` inside the stroke's `Y.Map`.** Concurrent appends to a `Y.Array` are CRDT-safe — both sets of stamps survive and merge. Render code reads `stamp.toJSON()` objects from the `Y.Array`. This is the standard Y.js pattern for concurrent list-like fields inside a structured type.

- **Option B — Accept LWW semantics; document as a known limitation.** Concurrent erasure loses one peer's stamps with ~50% probability. Uncommon but a real data-correctness bug.

- **Option C — Tombstone set: `erasedStamps` as `Y.Map<string, {x,y,r}>` keyed on stamp ULID.** Concurrent additions are CRDT-safe. Slightly more complex schema; stamps carry IDs they otherwise don't need.

**My lean: Option A.** Nested `Y.Array` is the correct primitive for concurrent list-like fields and is what the Y.js documentation recommends for this case. The cost is entirely in schema definition — zero runtime overhead. Option B is knowingly shipping a correctness bug. The "unlikely" argument is the same argument we would reject in any other context. Option C is more complex than necessary — `Y.Array` append semantics are sufficient since stamps are never removed.

### Decision 7 — Presence channel: Y.Awareness on `/yjs/<room-id>` vs. separate `/presence/<room-id>` JSON WebSocket

**Question.** Architecture.md § 3.2 specifies `/presence/<room-id>` as a separate WebSocket path serving "cursor / selection presence; JSON." Y.js ships `Y.Awareness` — a first-class protocol that travels on the same WebSocket as the Y.Doc sync and handles ephemeral peer state (cursors, names, colors) with automatic cleanup on disconnect. Should presence use Y.Awareness on the existing `/yjs/<room-id>` connection, or maintain the separate `/presence/<room-id>` JSON channel?

**Why it matters.** Y.Awareness is the standard Y.js presence mechanism. The browser-side `WebsocketProvider` already supports it; the server relay is ~20 additional lines using `y-protocols/awareness`. The separate JSON channel means double WebSocket connections per peer, double reconnect handling, and custom client presence code. This is a revision to a stated architecture.md design — it requires an ADR.

**Options.**

- **Option A — Use Y.Awareness on `/yjs/<room-id>`; eliminate `/presence/<room-id>`.** Single WS connection per peer. Automatic cleanup on disconnect. Zero extra client code. Revises architecture.md — needs an ADR.

- **Option B — Keep `/presence/<room-id>` as a custom JSON WebSocket.** Human-readable debug format. Double connections; double reconnect logic; custom client-side presence handling.

- **Option C — Y.Awareness for cursor/color/name state; custom server-push messages on the same `/yjs/<room-id>` channel for server-initiated events.** Single connection; extensible with custom envelopes. Requires careful framing alongside Y.js binary frames.

**My lean: Option A, and revise architecture.md.** Y.Awareness was designed for exactly this purpose. The `WebsocketProvider` already handles it on the client side — zero extra code. The server relay adds ~20 LOC using `y-protocols/awareness`. Double WebSocket connections (Option B) is unjustifiable complexity for ephemeral presence state that already has a correct CRDT solution. This revision requires an ADR.

### Decision 8 — Connection failure / reconnect UX

**Question.** What does the client show when the WebSocket drops? The existing app has no connection state concept. At M3, a disconnected user can still draw (y-indexeddb keeps the local Y.Doc operational), but peers won't receive updates. The user needs to know their sync state without being interrupted.

**Why it matters.** Silent disconnection is the worst outcome — user thinks peers see their changes, but they don't. A blocking modal is the second worst — it interrupts drawing. SPEC § 0 tenet: "snappy, sleek, user-friendly" overrides feature wishes.

**Options.**

- **Option A — Minimal corner status badge only.** Small indicator (connected / reconnecting / offline). Very subtle — may be missed.

- **Option B — Transient informational toast on state change.** ~3 s toast on disconnect: "Offline — drawing locally." ~2 s toast on reconnect: "Reconnected." Drawing never blocked. Uses the existing clearflow.ts / destructiveconfirm.ts toast infrastructure in informational mode.

- **Option C — Blocking "reconnecting" overlay.** Full canvas overlay while disconnected. Hard violation of the snappy tenet.

**My lean: Option B.** A transient informational toast makes the state change legible without blocking anything. Option A alone is too subtle; users who miss the badge continue assuming peers see their work. Option C is ruled out by the snappy tenet. The clearflow.ts toast host is already available and tested; an informational variant is a small addition.

### Decision 9 — In-flight stroke crash recovery: storage location

**Question.** Milestones.md M3 exit criteria: "client auto-saves the in-flight stroke every ~2 s during long strokes, so a tab crash mid-stroke loses at most a couple of seconds of pen movement." In-flight strokes are not in the Y.Doc — they are committed only at `pointerup`. Where does the auto-save write?

**Why it matters.** A tab crash is a process termination — in-memory state is gone. The auto-save must reach durable storage (localStorage or IDB) within 2 s to be useful. The server never sees in-flight samples by design.

**Options.**

- **Option A — Client-side localStorage slot (`whiteboard:stroke-wip`).** Every 2 s during a stroke, serialize current samples to localStorage. On app boot, check this slot; if non-empty, offer to restore or discard. Clear on `pointerup`. Synchronous; crash-durable; zero async complexity during the stroke.

- **Option B — Client-side IDB slot (`stroke-wip` store).** Same semantics as Option A but via IDB. Better for very large sample arrays (very long strokes at 200 Hz). Async write; must not add latency to the pointer handler.

- **Option C — Partial Y.Doc commit every 2 s as a "provisional" stroke.** Peers see the stroke forming. Changes the collaboration model; requires render-layer treatment for provisional strokes; scope expansion well beyond the exit criterion.

**My lean: Option A.** localStorage is synchronous, crash-durable, and zero-dependency. At 200 Hz over 2 s = ~400 samples × ~48 bytes = ~19 KB — well within localStorage limits. The restore-on-boot prompt is a lightweight UX touch. Option B is the correct upgrade for strokes longer than 30 s, which is not a primary use case. Option C changes the collaboration model and is scope creep the M3 exit criterion does not call for.

### Decision 10 — Migration from flat IDB to Y.Doc on first room open

**Question.** The existing `storage.ts` stores strokes as individual IDB rows in `whiteboard-local/strokes`. At M3, `y-indexeddb` takes over for synced rooms. Existing local strokes need a migration path into a new Y.Doc so users don't lose their work. What is the trigger, the data flow, and the rollback path?

**Why it matters.** Every user who has drawn anything before M3 ships has data in the flat IDB. Silent data loss on first room open is unacceptable. The migration must be opt-in, safe, and non-destructive.

**Options.**

- **Option A — Prompted migration on first room open if flat IDB is non-empty.** When the user navigates to their first `/b/<id>` and the flat IDB has strokes, show a one-time prompt: "Import your existing board into this room?" On accept: read all strokes, build a Y.Doc, commit, connect. On decline: open the room empty; flat IDB unchanged.

- **Option B — Explicit "Move to room" button on the home page.** Separate UI action. More discoverable; requires new UI surface.

- **Option C — Silent auto-migration on first WS connect.** Import all flat-IDB strokes into the Y.Doc without prompting. Risk: if the user has two devices, both auto-migrate, producing duplicate strokes in the server's Y.Doc.

**My lean: Option A.** A one-time prompt gives the user agency. The data flow: read all flat-IDB strokes → create a fresh Y.Doc → insert each stroke via the normal stroke-commit path → initialize y-indexeddb with this state → connect to server. After migration: write `whiteboard:migration-done` to localStorage; clear `whiteboard-local` (or mark it as migrated). Option C risks duplicate strokes across devices — a silent correctness failure. Migration status must be tracked explicitly to handle interrupted migrations (tab close mid-import).

### Decision 11 — Anonymous user name generation: server-issued vs. client-generated

**Question.** SPEC § 5: names are "random 'Adjective-Animal' by default, editable." SPEC § 10 "Still open": "Anonymous user names: server-issued vs client-generated. Decide at M3."

**Why it matters.** Server-issued names guarantee uniqueness but require a protocol message before presence can be announced. Client-generated names are instant (no round-trip) but may collide. Collision between two "Clever-Fox" instances is cosmetic — awareness state is keyed on client ID, not name.

**Options.**

- **Option A — Client-generated from a corpus; stored in localStorage as `whiteboard:peer-name`.** With 100×100 = 10,000 combinations, the probability of any two of 16 peers colliding is ~1.2%. No round-trip.

- **Option B — Server-issued on WS upgrade.** Guaranteed uniqueness for the session. Requires a custom protocol "hello" message — added complexity for a cosmetic feature.

- **Option C — Client proposes; server deduplicates.** Adds a protocol handshake round-trip for a cosmetic guarantee.

**My lean: Option A.** Client-generated names from a 100×100 corpus with localStorage persistence. This is how Figma, Google Docs, and Notion work. Collision probability at 16 peers is negligible. The user can edit their name anyway. Options B and C add protocol complexity for a cosmetic feature.

### Decision 12 — Snapshot pruning policy

**Question.** Architecture.md § 2.4 says "Old snapshots are pruned on a schedule (keep latest N, delete older)" — N is unspecified. A board active for 8 hours at 30 s cadence generates ~960 snapshots. What is N, and when does pruning run?

**Why it matters.** Unbounded snapshot growth inflates the SQLite file. Too few snapshots removes crash recovery margin.

**Options.**

- **Option A — Keep latest 3; prune synchronously on each snapshot write.** ~90 s recovery window. One `DELETE ... NOT IN (SELECT ... LIMIT 3)` — sub-millisecond on bun:sqlite.

- **Option B — Keep latest 10; prune asynchronously on a background timer.** ~5 min recovery window. Async avoids adding latency to the write path. Requires a background setInterval.

- **Option C — Keep only 1; overwrite semantics.** No recovery margin. Changes the schema PK from the architecture.md design.

**My lean: Option A (keep 3, synchronous prune on write).** Three snapshots is a meaningful recovery window without storage cost. Synchronous pruning on the snapshot write path is trivial in bun:sqlite. Option C removes crash recovery and changes the specified schema. Option B's background timer is unnecessary complexity for a single-process server.

### Decision 13 — Y.js version pinning and snapshot encoding format

**Question.** Which Y.js version do we pin, and which encoding format do we use for SQLite snapshots — V1 (`Y.encodeStateAsUpdate`) as architecture.md states, or V2 (`Y.encodeStateAsUpdateV2`, ~40% smaller)?

**Why it matters.** ADR 0003 says "pin a version; upgrade is an explicit ADR." If V1-encoded snapshots are in production and we later switch to V2, we need a migration. Mixing encoding versions in the same `snapshots` table requires a format discriminant.

**Options.**

- **Option A — Pin current stable Y.js (13.6.x); V1 encoding for snapshots.** Architecture.md specifies `Y.encodeStateAsUpdate` (V1). Compatible with all y-indexeddb / y-websocket clients at the same pinned version. No migration needed to upgrade encoding later unless we explicitly change it.

- **Option B — Pin 13.6.x; V2 encoding from day one.** ~40% smaller snapshots. Requires verifying y-indexeddb and y-websocket client also support V2 decoding at the same version.

- **Option C — V1 encoding + gzip compression via `Bun.gzipSync`.** Achieves similar size reduction to V2 without the encoding version question.

**My lean: Option A.** V1 encoding as architecture.md specifies. Snapshot size is not a constraint at M3 — even a large board's Y.Doc is well under 1 MB in V1. Record the exact pinned version (e.g., `yjs@13.6.x`) in ADR 0003 as a dated addendum. Revisit V2 only when snapshot size monitoring shows a real need.

### Decision 14 — Bun WebSocket API compatibility and Y.js package installation

**Question.** Y.js, y-protocols, y-websocket (client), and y-indexeddb are all pure JS with no native dependencies. None are currently in any `package.json`. Are there any known Bun incompatibilities to validate before committing to this dependency set?

**Why it matters.** ADR 0002 identifies "A subset of npm packages don't work cleanly on Bun" as a risk. Pure-JS npm packages are typically compatible. This is a prerequisite validation task, not a design decision — but it must happen as the first concrete action of M3.

**Concrete dependency additions needed for M3:**

| Package | Where |
|---|---|
| `yjs` | `apps/server`, `apps/web` |
| `y-protocols` | `apps/server` only |
| `y-websocket` (browser `WebsocketProvider`) | `apps/web` |
| `y-indexeddb` | `apps/web` |
| `uuidv7` or ULID library | `apps/web` — see note below |

**Note on UUIDv7.** Bun's `crypto.randomUUID()` generates UUIDv4, not v7. SPEC § 5 specifies "UUIDv7 → unguessable, sortable." Decide at brainstorm: add the `uuidv7` pure-JS npm package (~3 KB), use ULIDs (also time-sortable and unguessable, already used for `Stroke.id`), or explicitly relax the spec to allow v4. Do not silently ship v4 when the spec says v7.

**Action for M3 start:** Install these packages, run `bun typecheck`, and do a minimal WebSocket echo smoke test on Bun before building the relay. This is a gate, not a design decision.

### Decision 15 — Room lifecycle: idle TTL and MAX_ROOMS enforcement

**Question.** When `MAX_ROOMS=500` is reached, what happens? Are rooms ever automatically deleted outside of the owner-token `DELETE` endpoint?

**Why it matters.** Without auto-delete, MAX_ROOMS eventually caps the system. With an aggressive TTL, users lose work. For a self-hosted personal/team deployment (the intended use case), 500 rooms is enormous. For a public instance, it matters more.

**Options.**

- **Option A — Manual delete only; `POST /api/rooms` returns `429 Too Many Requests` when MAX_ROOMS is reached.** Admin uses `DELETE /api/rooms/:id` with the owner token to free space. Appropriate for self-hosted personal/team use.

- **Option B — Idle TTL: auto-delete rooms with no snapshot activity in N days.** Requires `last_active_at` monitoring (already have `updated_at`), a background setInterval cleanup job. Appropriate for public deployments.

- **Option C — Env-configurable TTL: `ROOM_TTL_DAYS=0` (disabled, default) enables Option A behavior; non-zero enables Option B.** Ships Option A by default; operator opts in to TTL.

**My lean: Option A for M3.** MAX_ROOMS=500 is very large for a self-hosted personal tool. Automatic room deletion adds implementation complexity and a risk of unexpected data loss at misconfigured TTLs. Document the 429 behavior and admin delete path in deployment.md. Option C (env-configurable TTL) is a natural M4 deployment polish addition if needed.

### Decision 16 — Client-side routing: how the SPA handles `/b/<id>`

**Question.** The server already has SPA fallback — any unmatched GET returns `index.html`. So `/b/<id>` already loads the SPA. But the current `main.ts` has no routing concept — it always boots, loads flat IDB, and starts drawing locally. At M3, the client needs to branch based on whether it's at `/` (local mode) or `/b/<id>` (sync mode).

**Why it matters.** The local-mode / sync-mode seam is the most architecturally significant new boundary in M3. Architecture.md § 2.1 designates `apps/web/src/sync/` as the M3 module. The routing logic is how this module is initialized. The sync bundle (Y.js + y-websocket + y-indexeddb = ~75 KB gz) should not be loaded eagerly in local mode — it should be lazy-imported only on room navigation.

**Options.**

- **Option A — URL-based branching in `main.ts` or a new `sync/index.ts`.** Read `location.pathname` on boot. If it starts with `/b/`, extract the room ID, lazy-import the sync module, enter sync mode. Otherwise enter local mode (current behavior). No router library.

- **Option B — Add a lightweight client-side router (e.g., `page.js`, `navaid`).** Two routes: `/` and `/b/:id`. ~2 KB gz. Given two routes, this is over-engineered.

- **Option C — Always in a room; `/` auto-creates and redirects to `/b/<id>`.** Every board is a room. Simplest sync layer (always on). Removes offline-drawing-without-server capability.

**My lean: Option A.** Two `if` branches on `location.pathname` in a new `apps/web/src/sync/index.ts` is all that's needed. No router library; consistent with the vanilla-TS approach. Local mode at `/` continues working as today. The sync module is dynamically imported (`await import('./sync/index.ts')`) so users in local mode don't pay the ~75 KB sync bundle cost. Option C removes the offline drawing capability that M0 specifically validated and that SPEC § 6 guarantees. Option B is over-engineered for two routes.

## 5. Risks and Unknowns

**R1 — Bun single-threaded event-loop assumption (Decision 5 lean).** The Decision 5 lean relies on JavaScript's single-threaded model guaranteeing that two concurrent WS upgrade handlers cannot truly race in Bun's current single-process model. This is correct today. If Bun introduces multi-threaded request handling (via Workers or otherwise), the guarantee breaks. The initialization code must include an explicit comment documenting this assumption so any future parallelism work triggers a review.

**R2 — Interrupted migration leaves corrupted state (Decision 10).** If the flat-IDB-to-Y.Doc migration is interrupted mid-import (tab close), the next boot finds a partial y-indexeddb state and an intact flat-IDB. Without explicit status tracking, the app cannot tell whether migration succeeded. Write `whiteboard:migration-status: 'in-progress' | 'done'` to localStorage before starting; clear only on success. On boot: if status is `in-progress`, offer to retry or reset to empty.

**R3 — erasedStamps CRDT correctness is not caught by basic integration tests (Decision 6).** If M3 ships with erasedStamps as a plain Y.Map array value (LWW), concurrent erasure from two peers silently loses work. This bug is not caught unless the test explicitly has two clients simultaneously erase the same stroke. Decision 6 must be settled before writing any client sync code, and the `packages/shared` typed Y.Doc wrappers must structurally enforce the correct schema so it is impossible to accidentally store stamps as a plain JS array.

**R4 — MAX_BOARD_BLOB_MB enforcement is unspecified.** The env var is declared (SPEC § 8) but what happens when a snapshot write exceeds 50 MB is undefined. At minimum: log a warning at 80% of the limit; at 100%, skip the snapshot (rely on the previous one) and log an error. Do not silently accept oversized blobs or let the server crash on a write.

**R5 — UUIDv7 vs. actual `crypto.randomUUID()` output (Decision 14).** Bun's `crypto.randomUUID()` returns v4. SPEC § 5 says v7. If we use `crypto.randomUUID()` without addressing this, we silently violate the spec. The functional impact is minor (rooms are not sorted anywhere visible), but the spec said v7 deliberately. Decide at brainstorm whether to add the `uuidv7` npm package, use ULIDs (already used for `Stroke.id`), or explicitly relax the spec.

**R6 — Web bundle size jump.** Current web bundle: under 30 KB gz. Adding Y.js (~50 KB gz), y-websocket client (~15 KB gz), y-indexeddb (~10 KB gz) adds ~75 KB gz if loaded eagerly. Total: ~105 KB — still under SPEC § 3.3's 150 KB gz limit. But the sync module must be lazy-imported for local-mode users (`/`) so they don't pay the cost. Verify bundle sizes at M3 close as part of the exit criteria.

**R7 — Offline-to-online Y.js state reconciliation must be explicitly tested.** The Y.js sync protocol handles offline divergence via state-vector exchange — this is Y.js's core value proposition. But it must be tested explicitly at M3: peer A goes offline; peer B makes changes; peer A reconnects; verify peer A has both their offline work and peer B's changes with no lost strokes. Do not close M3 without this test case passing.

**R8 — Presence performance at 16 peers.** Each awareness update (cursor move) triggers an awareness broadcast to all N-1 peers. At 16 peers with cursors moving at 60 Hz, the server handles up to 240 awareness messages per second. This is unlikely to be a bottleneck for a single-process Bun server, but it must be measured during the 16-peer exit criterion test. The capacity target exists specifically to bound this.

## 6. Suggested Brainstorm Question Order

For M2, the framework decision (vanilla vs. Solid) came first because the toolbar structure, reactive binding patterns, and bundle budget all depended on it. The M3 equivalent is the **relay implementation + Y.Doc schema** pair. Once those two are settled, every other M3 decision follows.

**Question 1 (hard gate): Relay implementation — Decision 1.**
Custom y-protocols relay vs. y-websocket server utility. This determines the server code's entire shape — Bun WebSocket API surface, room lifecycle, snapshot triggers, peer eviction, MAX_ROOMS enforcement. ADR 0003 is explicit; this should close in 10 minutes. If the lean (custom relay using y-protocols) holds, it unblocks all server design.

**Question 2 (hard gate): Y.Doc schema — Decision 6.**
How is erasedStamps stored in the Y.Doc? Nested `Y.Array` or LWW plain array? This gates `packages/shared` typed Y.Doc wrappers, the migration code (Decision 10), the render layer's Y.js read path, and the integration test design. A wrong answer here means a silent CRDT correctness bug that is hard to find in testing. Settle this before writing any client sync code.

**Question 3: Presence channel — Decision 7.**
Y.Awareness on `/yjs/<room-id>` vs. separate `/presence/<room-id>` JSON WebSocket. Once the relay design (Q1) is settled, this follows naturally — both paths use the same relay handler. If the lean (Y.Awareness, revise architecture.md) holds, this closes quickly and triggers an ADR. Spend 15 minutes.

**Question 4: Room creation flow — Decision 3.**
How does a user get a `/b/<id>` URL? This is a product/UX decision. The lean (client-generated UUIDv7 on "New board" click; server auto-creates on first WS connect) is clean, but this is where the user experience is defined and it deserves deliberate attention. Settle before implementation starts.

**Question 5: Auth model — Decision 2.**
Exactly how does the owner token flow? Should close in 10 minutes once Q4 is resolved. The lean (REST-only for admin mutations) is defensible; confirm it holds.

**Question 6: In-flight stroke crash recovery — Decision 9.**
localStorage vs. IDB vs. partial Y.Doc commit. Appears in the M3 exit criteria explicitly. The lean (localStorage slot) is clearly correct. Close quickly.

**Question 7: Migration from flat IDB — Decision 10.**
Settle after Q2 (Y.Doc schema) since the migration writes into the Y.Doc. The prompted-migration lean needs a UX decision: what does the prompt look like? Where does it appear?

**Questions 8–12 (quick closures):** User name generation (Decision 11), snapshot pruning (Decision 12), MAX_ROOMS enforcement (Decision 15), client routing (Decision 16), reconnect UX (Decision 8). The leans on all five are strong. Budget 30 minutes total.

**Questions 13–16 (resolve during implementation):** Y.js version pinning (Decision 13), package compatibility verification (Decision 14), admin mutation shape (Decision 4), room lifecycle TTL (Decision 15 upgrade path). These are better settled when the code is in front of you. Document the lean in the spec; implementer confirms or flags.

**The M3 spine: relay implementation → Y.Doc schema → presence channel → room creation flow. Settle those four and M3 has its architecture.**
